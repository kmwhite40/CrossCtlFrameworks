# A FedRAMP-compatible trust center (CDS rules)

Date: 2026-11-05. Status: steps 1–3 built; steps 4–5 planned. Base:
`feat/vdr-engine`.

## 1. Why, and by when

FedRAMP's Certification Data Sharing rules require providers to "use a
FedRAMP-compatible trust center to store and share FedRAMP Certification Data
with all necessary parties" (CDS-CSO-UTC). From the pinned consolidated rules
(2026.10.13.01), not from secondary sources:

| | obtain | maintain | grace |
|---|---|---|---|
| 20x | 2026-07-04 | **2027-01-01** | 2027-01-01, until next assessment |
| Rev5 | **2027-01-01** | **2027-08-01** | 2028-02-01 |

Classes B, C and D only. (A Coalfire summary citing 2027-08-01 was quoting the
Rev5 maintain date; both dates are right for their type.)

## 2. What Concord had (mapped 2026-11-05)

Two partial systems, neither a CDS trust center:

- `/trust` (`TrustProfile`, `TrustAccessRequest`): internal-only; its
  `published` flag is read by no code.
- The external portal (`ExternalAccessGrant`): good token grants (hashed,
  expiring, revocable, re-validated on every request, tenant re-clamped), but
  shares only authorization packages and evidence. **No CR26 deliverable was
  reachable by an outside party.**

## 3. Plan

Build on the portal; do not start a third system.

1. **Certification data, programmatically** (CDS-TRC-PAC, -HMR, -USH;
   CDS-CSO-CBF). *Built — §4.*
2. **Agency access inventory** (CDS-TRC-AAI): grants record who issued and who
   revoked them and when (today a bare `revoked` bool); an inventory and
   history view, exportable for FedRAMP on request.
3. **Access logging held six months** (CDS-TRC-ACL): log refused token
   attempts too; a per-grantee summary; revoke the app role's
   `UPDATE`/`DELETE` on `external_portal_audit_events` (it is labelled
   immutable and is not); keep the grantee's identity on the row so deleting
   a grant does not orphan its history.
4. **Self-service requests and denials** (CDS-TRC-SSM, CDS-UTC-AAD): an agency
   asks for access itself; approving issues a grant; denying starts a
   five-business-day FedRAMP notification clock that shows overdue when missed.
5. **Snapshots aligned to Ongoing Certification Reports** (CDS-CSO-HAD): today
   `cr26_documents` is overwritten in place.

## 4. Step 1 as built

- A grant's `scope.certification_system_ids` names the systems whose
  certification data it covers. Issuing one checks each system belongs to the
  organization and is not deleted; an assessment credential may cover only
  its engagement's own system.
- `agency` joins `EXTERNAL_PRINCIPAL_KINDS` — CDS-TRC-AAI's inventory is of
  agencies, so they are their own kind. Migration 0083 keeps its frozen
  three-kind list on purpose and reports `agency` rows as outside it; that is
  correct for 0083 and not changed.
- `GET /api/portal/certification-data` lists, and
  `GET /api/portal/certification-data/{system_id}/{kind}[?key=][&format=md]`
  serves, each document, authenticated by the grant token. Documented through
  the OpenAPI `certification-data` tag and the route docstrings.
- **Only schema-valid documents are shared.** `cr26.store` keeps invalid
  drafts by design; serving one as certification data would present an
  incomplete record as a filed one. The listing reports how many were
  withheld rather than implying there are none.
- **The formats cannot disagree** (CDS-CSO-CBF): the Markdown is generated by
  code from the JSON, every key and value appears in it, and both carry the
  SHA-256 of the canonical JSON (body and `X-Content-SHA256`).
- A document out of scope, of a deleted system, missing, invalid, or of a
  non-deliverable kind answers 404, and the attempt is logged `denied`;
  every read is logged `download` with its format.
- The portal page lists the documents with Read/JSON links, and the admin
  grant form gains the systems to share.

**Verified by mutation:** 14 guards; 13 killed. The one survivor, the
`organization_id` pin in `get_document`, is masked by RLS — `get_document`
clamps the session to the grant's tenant first, so a row filed under another
tenant is already invisible. It is defence in depth behind RLS, and the
end-to-end test proves the behaviour, not the line.

## 4b. Step 2 as built (CDS-TRC-AAI)

- Migration 0108 adds `issued_by`, `revoked_at`, `revoked_by` to
  `external_access_grants`, with `CHECK (revoked_at IS NULL OR revoked)`.
  `revoked` stays the access switch; the new columns say what happened.
- **The first revocation is the one kept.** Revoking an already-revoked grant
  succeeds and changes nothing (it used to write a second event); a second
  revoke must not move the date FedRAMP is told access ended.
- **Backfill reads the audit log**, actor and time from the same
  `external_grant` create/delete event. With no event, the columns stay NULL
  and the page says "not recorded" — no date is invented.
- `GET /api/admin/portal/certification-access-inventory?fmt=json|csv[&kind=]`:
  every grant that covers or covered certification data, ended ones
  included, all principal kinds (an assessor holding the data has access to
  it; `kind=agency` narrows). Each row: principal, systems (deleted ones keep
  their names), status from the same `grant_status` the access check uses,
  issued/revoked who and when, and certification-data downloads. The JSON
  carries the rule id, its statement read from the pinned rules, and the
  dataset version. Admin of that organization only.
- **The CSV is formula-safe** (CWE-1236): a cell that opens with `=`, `+`,
  `-`, `@`, tab or CR is prefixed with `'`. FedRAMP opens this file, and from
  step 4 agencies type their own names.
- The portal-admin page shows the inventory with CSV/JSON links. **How FedRAMP
  obtains it** (the rule's artifact): an organization admin exports the CSV
  and sends it on request.

**From the independent review** (four defects, none critical):

- A grant's kind must match a reused principal's; the API body defaulted
  `kind` to `customer`, which filed an agency's access under another kind and
  dropped it from `kind=agency`. Issuance refuses the mismatch, and the
  inventory reports and filters by the principal's kind.
- Listing the documents is access (it shows titles and digests): first/last
  access now include views; `downloads` stays downloads only.
- `revoke_grant` reads the row `FOR UPDATE`, so two concurrent revokes cannot
  both see it live and overwrite the first revocation.
- An active grant whose shared systems are all deleted reports `systems
  deleted`, not `active`.

**Verified by mutation:** 23 guards, all killed (two tests added for the
first-round survivors: a scope holding `[]`/JSON `null` passes the SQL
filter; a non-certification download must not count). The row lock is
pinned on the source, since a race test on one pool is not deterministic.

**Known limits:** a principal deleted after issuance (`SET NULL`) leaves its
grant's name blank — step 3 keeps the grantee identity on the row.

## 4c. Step 3 as built (CDS-TRC-ACL)

- **Append-only, six months, every role** (migration 0109). A trigger on
  `external_portal_audit_events` refuses UPDATE and refuses DELETE of a row
  younger than `interval '6 months'`. A REVOKE alone would bind only
  `ccf_app`; unscoped sessions run as the bootstrap superuser
  (`set_session_tenant`), so the trigger is what holds. `ccf_app` also loses
  UPDATE/DELETE. The one UPDATE allowed is the foreign key's own `SET NULL`
  of `grant_id`, and only with nothing else changed.
- **Organizations are never hard-deleted in production** (soft delete,
  DATA-04), so the trigger refusing a cascade that would erase recent portal
  history is correct. Test teardown that hard-deletes organizations uses
  `tests/portal_retention.py`, which disables the trigger inside its own
  transaction (table owner only).
- **The grantee is named on the row**: `grantee_name`, `grantee_kind`,
  `grantee_organization`, copied at write time and backfilled from the grant
  and principal. Deleting the principal or the grant leaves the history
  named.
- **Refused credentials are logged** (`refused`, detail = `revoked`,
  `expired`, `engagement ended`) at every resolution site: the API, the
  `/portal?token=` link, and the page's cookie. They are committed before the
  401, because the request session rolls back on the way out. One record per
  request, the cookie's grant first (the same order `_require_grant` resolves
  in). A token that matches no grant names no party and is not logged.
- `GET /api/admin/portal/access-log-summary?fmt=json|csv[&since=]`: per
  grantee, per month, per target, counts of each access action. `issued` and
  `revoked` are what the provider did, not access, and are left out; any
  other action lands in `other`. It also gives `oldest_event_at`, so a short
  record reads as little history, not little access.
- `GET /api/portal/access-log`, by the grantee's own token: every event on
  that grant ("as it pertains to specific parties … available upon request by
  those parties"). Reading it is logged too. The portal page links it.

**From the independent review** (nothing critical; five fixed):

- A dead token replayed without limit wrote a permanent row each time, into
  a table nobody may prune for six months. A refusal is now logged at most
  once per grant, reason and 10-minute window (`REFUSAL_LOG_WINDOW`); a log
  that cannot be edited cannot count, so the repeat is skipped, not counted.
- The SET NULL exemption could not tell the foreign key from a person: anyone
  holding UPDATE could detach a live grant's events from its party's log. The
  trigger now also requires the grant row to be gone.
- TRUNCATE skips row triggers; a statement trigger refuses it.
- The teardown helper re-enables the trigger only on success, so a failure
  shows its own error.
- One assertion could not fail; replaced by tests for the above and for the
  refused organization delete.
- Not changed: exchanging a link token for the cookie is not itself logged.
  It serves no data, and the page it redirects to logs the view.

**Verified by mutation:** 22 guards; 21 killed, including the trigger and
migration guards, run through the 0108 round trip so the mutated migration
actually reaches the database. The survivor is the trigger's `ROW(...)`
comparison, and it is equivalent: with the grant row required to be gone,
the only UPDATE that reaches it is the foreign key's own, which changes
nothing else. It stays as defence in depth.

## 5. Not done in step 1

- No FedRAMP ID on documents (CDS-CSO-FID) — no FedRAMP ID field exists yet.
- Availability reporting (CDS-CSO-AVR) and per-service materials
  (CDS-CSO-PSM, MUST for Class D) are untouched.
- The `/trust` page is still internal; it is not the CDS trust center and is
  not presented as one.
