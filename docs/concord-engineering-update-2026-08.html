What we built

assessment pipeline, end to end

Concord can now take a raw evidence document and carry it all the way to a proposed control finding — with every verdict traceable to the passage and the model that produced it, and a human gate at the only point where it becomes authoritative.

Shipped

Evidence preparation & retrieval

Documents are parsed, screened against the control catalog, expanded, classified and embedded — each stage persisted separately so a failed run resumes where it stopped rather than starting over. Retrieval fuses vector similarity with full-text ranking, so a passage can surface on meaning or on exact language.

Shipped

Objective-level assessment

The engine evaluates 800-53A objectives individually and rolls them up into a control finding. It proposes — it never writes an assessment result. An assessor accepts, and acceptance is the only path to an authoritative record.

Shipped

AI provenance

Every classification and verdict now has a recorded run: model, provider, prompt version, input and output hashes, and one citation row per passage cited. Accepting a finding stamps the reviewer onto those runs, so which model produced this, from what evidence, and who signed off is a single query.

Shipped

Calibration harness

Assessors can now record that a proposed finding was wrong, with the finding they believe correct. That turns routine review into labelled data.

The two error directions are reported separately and never averaged. A control that passed and should not have is a missed finding in an authorization package; the reverse is wasted remediation effort. Collapsing them into one accuracy figure would hide the number worth watching.

Shipped

Closure & remediation loop

An accepted other-than-satisfied finding now becomes a POA&M automatically, and closing that POA&M queues a fresh look at the control. The loop used to be open at both ends: findings that never became tracked work, and remediation that never triggered re-assessment.

Shipped

AI dissent path

A second model argues the opposite case against any satisfied verdict, reading the same passages. Genuine disagreement routes the objective to insufficient evidence — a state that already blocks acceptance. Two verdicts are never averaged or majority-voted; that would manufacture precision that isn't there. Off by default, since it doubles model calls on the passing subset.

What we declined to build

and what that turned up instead

Three capabilities on the roadmap were investigated and cancelled. In each case Concord already had the capability, or the gap wasn't worth a slice. Every cancellation was cheaper than the feature — and each one surfaced a real defect that the feature work would have walked past.

Declined

Generated-artifact validation

Already built. Concord validates OSCAL documents against the official schema, scores SSP completeness, and enforces closed-set citations — two of which go beyond the capability we were proposing to copy.

Found instead: a health check that reported the OSCAL exporter healthy without validating anything. Its test only asserted the check appeared in the list by name.

Declined

Project-context assistant

The one genuine gap — open-ended Q&A over the project — is a surface Concord has deliberately avoided for citation-bearing output. Building it would cut against a safety property, not fill a hole.

Found instead: the module that drafts SSP narrative prose had zero test coverage, and every tenant's draft was being generated on a shared global API key rather than their own configured provider. Both fixed.

Declined

Continuous-verification drift records

Concord's continuous monitoring, scheduled control tests and scan reconciliation already cover this ground, and cover it well.

Found instead: failing control tests opened remediation tasks and POA&Ms that nothing ever closed when the control recovered. The backlog was filling with entries that looked like live findings and weren't. Now fixed — the task resolves, and the POA&M is surfaced for a human rather than auto-closed.

“Closing a POA&M asserts, in an authorization package, that a weakness is remediated. A single passing test is not that assertion.”

This is why recovery surfaces a POA&M rather than closing it — and why a passing re-assessment proposes rather than decides. The engine never retires its own finding.

Tenant isolation

the largest single fix

An audit found that eleven tables built during this cycle had no row-level security policy, while 110 others in the same schema did. Isolation rested entirely on application-level checks with no database backstop.

Hardened

Policies on all eleven tables

Each carries an enforced tenant_isolation policy, verified by testing that one organization genuinely cannot see another's rows — not merely that a policy exists. A registry test now fails if any future table with a tenant column ships without one.

Hardened

Background workers scoped

Both job queues now process each job under its own tenant, so the paths that write the most rows are covered too. The claim query stays deliberately cross-tenant — it reads only job identifiers — and that exception is documented rather than left unstated.

Hardened

Two traps worth knowing

A database rollback silently undoes the tenant context — and because an unset tenant means bypass, it fails open rather than closed. Every affected path was audited; all were already contained, and the misleading docstring that implied otherwise is corrected.

Separately, a scheduled job failing at the database level could abort the entire nightly cycle for every tenant, because the error was caught in Python while the transaction stayed poisoned.

How the defects were found

a practice worth keeping

Roughly two dozen defects surfaced this cycle. Almost none were found by reading code. They were found by deleting a guard, re-running the tests, and checking whether anything noticed.

The expensive cases were tests that passed for the wrong reason — they looked like coverage and weren't:

  • A fixture with one error of each kind passed against code that had the two branches swapped. Balanced test data proves nothing about which is which.
  • A cross-tenant test passed because the database filtered the row before the application check ever ran — leaving that check entirely unverified.
  • An insert test was satisfied by the wrong policy clause, so it never tested the one it claimed to.
  • A best-effort error handler made “skipped correctly” and “crashed and was swallowed” look identical from outside. Three separate findings traced to this.

The rule we landed on: when a mutation produces no failure, the question isn't “which mutation will fail?” — it's whether the guard is untested or the hazard is designed out. Those need different responses, and only checking the adjacent mutation tells them apart.

The platform around it

capabilities in place today

This cycle's work sits on top of an existing surface. For anyone who hasn't looked at Concord recently, here is what it already covers.

Authorization packages

SSP, SAR and POA&M generation with OSCAL export, validated against the official schema. Packages carry provenance, and any two can be diffed or replayed to show what changed between submissions.

Continuous controls monitoring

Vulnerability scans ingest and reconcile into POA&Ms automatically, closing and reopening as findings come and go. Control tests run on a schedule, with optional machine-checkable assertions rather than a human attesting.

Evidence repository

Versioned evidence with confidence scoring and reproducibility tracking, so a citation in a package resolves to a specific artifact at a specific point in time.

Personnel & access

The workforce security lifecycle end to end — position risk designation, background screening, security training, and periodic access reviews, each mapped to the control it satisfies (PS-2, PS-3, AT-2, AT-3, AC-2).

Vendor risk

Security questionnaires with reusable templates, sent and tracked through response, so third-party assessments live alongside the rest of the evidence rather than in a spreadsheet.

Assurance graph

A queryable model of the authorization — the digital twin — backed by a registry of deterministic queries, so posture questions are answered from data rather than assembled by hand.

Collaboration portal

An external surface for auditors and assessors to work a request list without needing accounts in the main application.

Enterprise identity

OIDC single sign-on and SCIM provisioning, with row-level tenant isolation enforced in the database across 121 tables.

AI governance

A typed action layer for AI operations with human approval gating, plus governance records for the agents themselves — so model-assisted work is reviewable rather than opaque.

Compliance packs

Framework content ships as versioned packs, so a new baseline or an updated catalog is a data change rather than a release.

Two product changes are worth calling out separately. The primary navigation was consolidated from eleven top-level items to five, which is the difference between a tool people can learn and one they need training for. And Concord now runs its own assurance against itself — the platform is assessed by the platform, which means the team finds the rough edges before a customer does.
