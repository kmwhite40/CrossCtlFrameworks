Where the build stands

as of head 513e486

Concord is feature-complete across the authorization lifecycle: a customer can define what compliance means for them, authorize a system against it, operate the program day to day, and report on it — without leaving the product. The catalog layer, the authorization-package pipeline, continuous monitoring, and the governance surfaces are all shipped and in the main line.

What changed this cycle is the shape underneath. The platform used to be control-first: narrative was authored per control, and every framework a customer added meant authoring it again. It is now capability-first — a capability is described once and reaches every framework through the existing crosswalk. That was the root gap in the product, and it is closed.

The honest edge of the build is live machine evidence. Concord reads real posture from two providers today. Everywhere else, evidence is human-attested or ingested — which is a working compliance program, but it is not the continuous-verification story, and this report does not tell it as one.

five areas, forty surfaces

The product is organized the way an authorization actually runs: define compliance → authorize systems → operate the program → report on it. Every item below is a shipped, reachable surface with an API behind it.

Platform capabilities

true everywhere, not a feature

Multi-tenancy

Row-level security enforced by PostgreSQL across 137 tenant-owned tables. Isolation is a database property, not an application convention — and a test fails the build when a new table escapes it.

Identity

OIDC single sign-on with just-in-time provisioning and SCIM, session and bearer authentication, and separation-of-duties RBAC on writes.

Tamper evidence

Every mutation lands in a SHA-256 hash-chained audit log. A changed or removed record breaks the chain.

Fail-closed defaults

The application refuses to start in a non-dev environment without auth enabled, a strong session secret and explicit CORS origins. Account lockout, password policy, login rate limiting and security response headers are on by default.

Provenance

Ingestion runs record the SHA-256 of their source with stats and timings; AI calls record model, provider, prompt version and input/output hashes with a citation row per passage.

Interfaces

481 REST endpoints with OpenAPI docs, a 63-template HTMX web UI, and a 26-command Typer CLI over the same service layer.

Deployment

Docker and Compose, Alembic-managed schema at a single head, and a reliability self-check for readiness.

Supply chain

CI runs ruff, mypy strict, bandit SAST and the full suite against a real Postgres, plus CycloneDX SBOM, pip-audit and Trivy. A non-conformant OSCAL export fails the build.

What landed this cycle

seventeen pull requests, all merged

The cycle's theme was foundations: the ontology that removes per-framework narrative duplication, and the posture spine that gives machine evidence somewhere to land. Both were sequenced deliberately ahead of the features that need them.

Shipped

Capability ontology

A capability is authored once and carries edges to the canonical control, system components, risks and indicators. One capability annotating three controls reaches CMMC, FedRAMP and ISO through the existing crosswalk — verified end to end.

Status derivation writes a sibling field and never creates a row, so derived signal can never quietly assert something about a control nobody claimed.

Shipped

SSP narrative from capability

Edit one capability, re-render every control it maps to. This is the duplication the ontology existed to remove, now visible in the product.

Shipped

Per-resource posture findings

A check now names which resources failed rather than returning a single verdict, and a deterministic check beats a model verdict where both exist. It writes through the existing control-test path — one results table, one vocabulary, one POA&M loop.

Shipped

Live provider posture

Microsoft 365 / Graph: MFA registration, legacy authentication blocked, stale accounts. PuppetDB: whether the fleet is reporting, and whether declared state is actually being enforced.

Report-only enforcement does not satisfy a check, and a missing API permission reports as unrunnable — a 403 must never read as a clean fleet.

Shipped

Desired state as data

Posture checks are declared in packs rather than coded, and pack sources can be polled from a Git repository and adopted on review — GitOps for compliance content.

Shipped

Closed-loop remediation, waivers, drift

A failing check produces a remediation plan and closes when it recovers; a finding can be waived with an approver instead of deleted; drift is retained on a schedule; and change impact answers what a configuration change would do to the authorization before it is made.

One defect fixed along the way: the failing-resources view was reporting resources that had already been fixed.

Shipped

Flaw remediation against SI-2

Remediation measured against declared timeframes and organized into waves. Formally accepted risk became its own bucket rather than an SLA breach.

Operators should know: the compliance percentage can fall on the first read after upgrade. A young accepted-risk POA&M used to count as compliant — accepted on day three and credited as remediated. The same rows are now counted honestly.

Shipped

DISA CCI as an authoritative source

5,149 CCIs and all 10,216 of their references across 800-53 v3, Rev 4, Rev 5 and 800-53A, with the reverse index the platform lacked: a scanner finding that names only a CCI now resolves to controls.

Shipped

Live catalog sources

Upstream OSCAL is polled with conditional requests and content hashing, revisions are retained, and adoption is gated on human review. Detection and loading used to be disconnected; they are now joined.

Hardened

Two critical unauthenticated RCEs

Patched in the landing site's dependency tree, along with six other advisories. Both dependency trees are now clear.

Hardened

Role names the system cannot hold

Several routes named roles outside the actual role enum, which silently collapsed to admin-only — endpoints that read as broader than they were. Corrected, and the same defect was found and fixed in the waiver approver list.

The CR26 certification profile

all merged
Shipped

CR26 schema spine

Merged. FedRAMP's eleven CR26 schemas are vendored and pinned by SHA-256, documents validate against them entirely offline, and the eleven are watched for upstream drift.

One measured caveat that shapes everything built on top: this environment enforces the date format but not date-time or uri, because the optional validator libraries are absent. A malformed timestamp therefore validates clean. The seeders below are written to be correct by construction rather than trusting the validator to catch it, and every date they emit is pinned by an exact-string test.

Shipped

CR26 deliverables — every one a provider files

The Certification Package Overview and the Security Decision Record are generated from what the platform already holds: SSP control narrative, assigned parameter values, KSI validation results and assessor findings. Authoring is admin-only, and a re-seed refreshes every derived field while preserving the one thing the platform cannot derive — the human-written narrative.

The three Vulnerability Evaluation and Reporting documents — Vulnerability Detail Report, Accepted Vulnerability Info, and the machine-readable historical record — are generated from the POA&M table. These carry the programme's earliest deadline: mandatory 2026-12-07, ahead of CPO and SDR maintenance.

A seeded document reports what it could not say. A vulnerability with no identification date, no detection source or no description is left out and named, because the deliverable's own to-do list is worth more to an operator than a document that quietly looks complete.

Three more have since landed. The Ongoing Certification Report inverts the others: eight of its nine required fields are statements only a human can make, so it is seeded as a scaffold and stays invalid until someone writes them — the validation errors are the author's to-do list. A document that validates is a document somebody can file, and one of its empty values is a formal attestation that no security incidents occurred, which the platform has no way to know.

Incident Reports and Significant Change Notifications are filed per incident and per change rather than per system, so each filing is stored under its own key: advancing an incident from Initial to Ongoing to Final keeps all three rather than overwriting the record of the last one.

That is every CR26 deliverable a cloud service provider files. The two not built — Advisor Information and Assessor Information — are published by assessment firms about themselves, on their own websites. They describe a company rather than a system, and building them here would file a document about somebody else against a customer's system.

Shipped

CR26 vocabulary

Already merged. CR26 replaces the provider-side POA&M with a list of Accepted Weaknesses — and the platform already stored the weakness, so nothing about what is stored changed. An existing POA&M row classifies as accepted, not accepted, or unknown, with no second table to disagree with the first.

Certification Class (A–D) and Path are stored as independent axes. FedRAMP is explicit that a Class is not a replacement for an impact level, and the published ranges overlap — so nothing derives one from the other, and a build guard fails the build if anything starts to.

What a filed document is allowed to say

six defects found and closed

A compliance document can pass every schema check and still assert something untrue. That class of defect cannot be caught by validation, so it is hunted deliberately: each value the platform writes is audited against “is this true?” rather than “does this validate?”. Six were found and closed this cycle. Each is stated here with what it would have put in front of an assessor, because the guarantee is only worth what the evidence behind it is.

Hardened

A document cannot claim evidence nobody captured

An implementation statement omits its manual-evidence caveat only when this organization’s own connector has completed a recent, non-empty sync. The check previously asked whether Concord ships a connector for the declared platform — so a customer who had configured nothing still produced clean, uncaveated statements, while a customer on a platform with no connector had every statement flagged. The safe direction was inverted for the two most-used platforms.

One consequence is visible and deliberate: coverage percentages fell for tenants without a healthy connector. Their posture did not change; the number stopped overstating it.

Hardened

A platform is never guessed

“No cloud platform” is one of four answers the intake questionnaire offers. A customer who chose it — or who runs anything outside the three supported platforms — previously received a system security plan describing Microsoft 365, naming Entra ID, Purview and Intune as the mechanisms implementing their controls. Six separate defaults resolved an unknown platform to a real product name.

“None” is now a platform in its own right, with an empty service catalogue, so nothing platform-specific can be drafted for it. An unrecognised platform stays distinct from a declared absence: the first means the platform does not know, the second means the customer said so.

Hardened

Machine-drafted text is always marked as machine-drafted

Under the platform’s own rule, a draft marker in stored narrative is the only durable record that text has not been human-reviewed. The seeder — which writes the first narrative for every control — did not write that marker. On a freshly seeded plan, 27 of 110 entries carried it; the other 83 were machine text that the interface displayed as human-authored.

Every producer now marks its output. A newly seeded plan therefore shows the AI-assisted badge on every control and scores lower on completeness until reviewed — correct, because it genuinely is unreviewed.

Hardened

The generator cannot overwrite human work silently

Regenerating implementation statements replaced every narrative in a plan, including text a person had written and cleared, and reported only how many entries it touched. Human-cleared narrative is now preserved by default and the affected controls are named. Replacing it is still possible, deliberately, and every control affected is listed — destroying human work on request is legitimate; doing it without a record is not.

Shipped

Where this system stands, in six steps

Forty surfaces grouped by product area tell a new customer nothing about where to start. Each system now carries an ordered path — intake, evidence connection, the security plan, closing gaps, producing the package, bringing in an assessor — with each step’s state computed from the records themselves and the remaining work named rather than counted.

A step reports unknown when the platform cannot see enough to judge, which is never shown as done. Steps move backwards: a lapsed connector or an expired engagement takes its step with it, because a progress bar that only rises would be false the day something expires.

Shipped

Independent assessors, scoped and time-bound

A third-party assessment organization is modelled as what it is — a firm external to the provider, engaged for one system over one period. It never receives an internal account, which is what independence requires. An engagement carries the relationship; credentials hang off it, so a token can rotate or a second assessor can join without a second identity, and ending the engagement ends every credential under it at once.

A credential stops working when its engagement ends, whatever its own expiry says. Where the provider and the assessor share a mail domain the platform records what it observed and never blocks — independence is a matter of ownership and contracts that no field here can settle.

What the platform can prove about itself

measured, not reviewed

Tenant isolation and tamper evidence are the two properties a compliance platform cannot ask to be taken on trust. Both were audited by deleting each guard and re-running the suite — because reading the code had already missed these twice. What that found is stated here in full, including what it says about the tests that were supposed to be watching.

Hardened

Half the tenant-isolation tests could not fail

A route’s own organization check, exercised only over HTTP, cannot be shown to exist: the database’s row-level security refuses the foreign row first, so deleting the application check leaves the test green. Of 38 cross-tenant tests, 19 were proving the database worked rather than the code — and three separate tests all passed when the shared system-scoping guard was removed.

Each is now pinned where the guard actually lives, on a session with row-level security bypassed — the path the command line, scheduler and workers use. Two exports had no cross-tenant test at all.

Hardened

Fifty routes now check the tenant themselves

Twenty-six routes that took a record id relied entirely on the database policy; eleven more trusted an organization named by the caller in a request body rather than the authenticated one; thirteen server-rendered pages had no check at all. Every one is now guarded in the application, with the database policy as the backstop it was designed to be rather than the only line.

Among them: a document download that returned bytes on an existence check alone, and an assessment engagement that could name another organization’s system — recording a third-party assessor’s scope over a system nobody authorized.

Hardened

The tamper-evidence chain was forking on ordinary traffic

The audit log is append-only and hash-chained, and verification had been failing intermittently for long enough that a test comment called it “the one accepted full-suite flake.” It was neither flaky nor a test problem. A tenant policy added to the audit table filtered the query that reads the chain’s head, so a writer that could not see the true head linked its row to the beginning of the chain. Two organizations writing in the same window was enough.

Two further causes surfaced only by measuring after the first was fixed: simultaneous writes both reading the head before either committed, and two events in one transaction. Verification detects a real alteration as before — including a forged row that hashes itself correctly and only fails to link, which is the one shape a content check cannot catch and the exact shape these defects produced.

Hardened

Every audit event now names the tenant it belongs to

The non-HTTP audit path never recorded an organization, and a record without one is deliberately visible to every tenant — so events from the external portal, compliance packs, waivers, patching, enforcement, AI governance and identity provisioning were readable across organizations.

All 35 recording sites were classified individually rather than patched wholesale. Thirty-three belong to a tenant; two are genuinely deployment-wide and stay visible to everyone, because a customer whose catalog moves beneath them is owed that record. The fault was not that a blank means “everyone” — it is that blank was also the default, so “this belongs to no one” and “someone forgot” were the same value. Omitting it is now an error the compiler catches.

Hardened

The production configuration was never exercised

The test suite runs with the environment set to test, which the platform treats as development — so the production branch of eight security gates had no coverage: the strict-transport header, five session-cookie Secure flags, and two mock paths meant to be unavailable outside development. A gate written the ordinary way passed with the gate deleted.

The readiness check had drifted further: it carried its own idea of what “development” means and reported “open access is expected” about a deployment every other part of the platform was treating as production. One definition now, and the production side of each gate is tested.

What the build will not claim

read this before a customer conversation

These are current boundaries, not defects. Each is a place where the product could be oversold, so each is stated plainly.

Limit

Live machine evidence is three providers deep

Nine automated posture checks: five across Microsoft 365 / Graph and PuppetDB, and four over AWS GovCloud, which previously captured configuration that nothing evaluated. Azure Government now has a capture connector; Google Cloud does not, and a GCP customer’s plan says so rather than borrowing another provider’s catalogue.

A claim of automated evidence now requires that this organization’s own connector completed a recent, non-empty capture — not merely that a connector exists for the platform. Everything else is human-attested or ingested evidence, and says so.

Limit

Plans written before this cycle may name the wrong platform

Until the platform default was fixed, an unrecognised or absent cloud platform resolved to Microsoft 365. A plan written then is now indistinguishable from one legitimately on that platform, and rewriting it would be a second guess on top of the first.

The intake answer is retained separately from the plan, so a readiness check reports every plan whose platform disagrees with what its system declared. The decision is left to a person; the platform names the candidates and does not act on them.

Limit

The M365 checks have not been run against a live tenant

Evaluators are pure and tested against recorded Graph responses. Confirming a check reads a given tenant requires that tenant's app registration, which the team does not hold.

Limit

AI proposes; it never decides

The model layer is optional and off by default. It drafts narrative and proposes findings, always marked as draft, always citation-bearing, and an assessor's acceptance is the only path to an authoritative record. There is deliberately no open-ended assistant over project data.

Limit

There is no official FedRAMP 20x OSCAL package

FedRAMP publishes requirements; NIST publishes OSCAL; Concord generates its own. The community-maintained KSI catalog is not the system of record here, and should not be described as one.

Limit

The README's status section is stale

It still reports 54 migrations and 720-plus tests against an actual 79 and 2,745. Nothing in the product is wrong — the summary prose simply has not kept up with two cycles of work. Worth correcting before it is quoted somewhere that matters.

Limit

An acceptance rationale lives inside the document it appears in

CR26 requires a written rationale for every accepted vulnerability, and no column in the platform holds one — so an administrator authors it into the deliverable, and each re-seed preserves it. That works until a reporting window moves backwards past an accepted vulnerability: the row falls outside the new period, the stored document is replaced, and the rationale is gone with nothing reported at the moment it happens.

It is named here rather than smoothed over because it is the one place in this family where work disappears silently, and that is precisely what the rest of the design exists to prevent. The fix is to give the rationale a durable home of its own rather than a home inside a generated document. Until then: do not move a reporting window backwards past an accepted vulnerability without re-authoring afterwards.

What comes next

sequenced, not a wish list

The foundations were built first precisely so this list is additive. In rough dependency order:

  • Identity and crypto hardening — MFA and PIV-CAC, SSO hardening, KMS-backed key rotation and FIPS-validated cryptography.
  • Marketplace status reporting — blocked on a source, not on engineering. FedRAMP publishes no status vocabulary this platform can read, and the five-per-regime lists exist only in an unadopted draft RFC. What each system carries instead is Concord’s own pipeline stage, barred by test from any filed deliverable.
  • Google Cloud — Azure Government now has a capture connector; GCP does not, and a GCP customer’s system security plan correctly declares no cloud platform rather than borrowing another provider’s. Supporting it means a service catalogue and a responsibility model, not a connector alone.
  • FedRAMP-assigned parameter values — the Rev 5 baseline overlay. Every organization-defined parameter now carries its label, guidance and choices from the catalog, and an assessor can see which are unset. What does not exist anywhere in the data is FedRAMP’s own assigned values: the workbook’s FedRAMP columns are membership markers, and one cell says plainly that a provider “may use FedRAMP value” without carrying one. It needs FedRAMP’s published OSCAL baselines ingested as a new source.
  • Integrations — eMASS, Jira, and wiring the typed AI action path to the organization's own gateway.

The one thing to take from this report: the product is broad and the foundations are now right, but breadth of live machine evidence is the gap between "a compliance program that runs in Concord" and "an authorization Concord continuously verifies." Everything needed to close it is built. What remains is providers.
