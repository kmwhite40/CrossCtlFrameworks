Where the build stands

as of head 95e6ba0

Concord is feature-complete across the authorization lifecycle: a customer can define what compliance means for them, authorize a system against it, operate the program day to day, and report on it — without leaving the product. The catalog layer, the authorization-package pipeline, continuous monitoring, and the governance surfaces are all shipped and in the main line.

What changed this cycle is the shape underneath. The platform used to be control-first: narrative was authored per control, and every framework a customer added meant authoring it again. It is now capability-first — a capability is described once and reaches every framework through the existing crosswalk. That was the root gap in the product, and it is closed.

The honest edge of the build is live machine evidence. Concord reads real posture from two providers today. Everywhere else, evidence is human-attested or ingested — which is a working compliance program, but it is not the continuous-verification story, and this report does not tell it as one.

What a customer can do

five areas, forty surfaces

The product is organized the way an authorization actually runs: define compliance → authorize systems → operate the program → report on it. Every item below is a shipped, reachable surface with an API behind it.

Compliance

define what applies
Control catalog
5,400 NIST SP 800-53A Rev 5 assessment objectives, browsable and faceted, with each control's cross-framework mappings grouped in place.
Framework crosswalk
35 classified frameworks — FedRAMP, CMMC, 800-171, HIPAA, HITRUST, ISO 27001, SOC 2, CIS v8, CSF, GDPR, StateRAMP, CJIS, MARS-E, the DoD SRG impact levels, CNSSI 1253, DISA CCI, the three major clouds. Answer once, see where else it counts.
Capability ontology
Describe a capability once — it maps to the canonical control and reaches every other framework through the crosswalk, instead of being re-authored per framework.
Coverage & gaps
Coverage view across baselines, including inherited controls, so the unclaimed set is visible rather than inferred.
Compliance packs
Framework, control, evidence and rule content ships as versioned packs — a new baseline is a data change, not a release. Packs can be polled from a Git repository and adopted on review.
Catalog currency
Upstream OSCAL sources are polled for drift with retained revisions and gated adoption; a catalog never changes under a customer without a human accepting it.
Search & worksheets
Postgres full-text search across the catalog, the raw source workbook tabs, and a version-to-version workbook diff.

Authorization

get the system authorized

First-class components, inventory items, per-type information types and interconnections — with boundary and data-flow diagrams generated from the model, so they cannot drift from it.

A real NIST 800-53 Rev 5 SSP: the authoritative 800-53B baseline for the system's impact level (287 controls at Moderate), organization-defined parameters scaffolded from the catalog, exported as OSCAL and as a FedRAMP-style Word document. CMMC L2 / 800-171 generation is unchanged alongside it.
Assessments & SAR
Run an assessment, record control-level findings, and export OSCAL assessment results with evidence observations and open POA&Ms carried as risks.
Authorization package
SSP + SAR + POA&M + component-definition as one ZIP, every document validated against the official NIST OSCAL v1.1.2 schema. Absent artifacts are omitted and noted, never fabricated.
Package provenance
Packages carry provenance and can be diffed or replayed, so what changed between two submissions is a query rather than an argument.
FedRAMP 20x
51 Key Security Indicators across the 10 published families, a deterministic validation engine over machine-readable rules, and readiness scoring — kept separate from Rev 5 but traceable to NIST through each indicator's control mapping.
Live scoring

Assurance graph

Operations

run the program
Evidence repository
Versioned evidence with review workflow, WORM lock, confidence scoring and reproducible digests — a citation resolves to a specific artifact at a specific time.
Evidence preparation
Documents are parsed, screened against the catalog, expanded, classified and embedded, each stage persisted so a failed run resumes where it stopped. Retrieval fuses vector similarity with full-text ranking.
Objective-level assessment
The engine evaluates 800-53A objectives individually and rolls them into a control finding. It proposes; an assessor accepts, and acceptance is the only path to an authoritative record.
Scan ingestion
Nessus, Inspector and CSV scans ingest and reconcile into POA&Ms automatically, opening and closing as findings come and go.
Control tests
Scheduled control tests with machine-checkable assertions, per-resource findings rather than a single verdict per control, and recovery that surfaces the POA&M for a human instead of silently closing it.
Live posture
Configuration read from live provider APIs and evaluated per resource — Microsoft 365 / Graph and PuppetDB today. A permission error is reported as unrunnable, never as a clean fleet.
Drift & telemetry
Configuration drift over time with retention control, plus change-impact analysis: what a proposed configuration change would do to the authorization before it is made.
Closed-loop remediation
A failing check produces a remediation plan through a provider registry, and the loop closes when the check recovers.
Flaw remediation (SI-2)
Remediation measured against declared SLA timeframes and organized into waves. Formally accepted risk is its own bucket — accepting a risk cannot improve a remediation score.
Waivers
Accept a finding without erasing it: the waiver is a record with an approver, not a deletion.
POA&Ms & risks
Plan of action and milestones, a risk register with residual risk, and the aging and SLA views over both.
Personnel & access
The workforce security lifecycle — position risk designation, screening, security training and periodic access reviews, each mapped to the control it satisfies.
Vendor questionnaires
Third-party security assessments with reusable templates, tracked through response and scored, alongside the rest of the evidence.
Audit workspace
Engagements, evidence requests and findings, for working an actual audit rather than exporting to a spreadsheet.
Regulatory change
Framework and regulatory updates tracked as they land.
AI governance
AI agents governed as privileged non-human actors — risk scoring, a kill switch, and a typed, citation-first action layer that requires human approval. Optional and disabled by default.

Platform capabilities

true everywhere, not a feature

Multi-tenancy

Row-level security enforced by PostgreSQL across 137 tenant-owned tables. Isolation is a database property, not an application convention — and a test fails the build when a new table escapes it.

Identity

OIDC single sign-on with just-in-time provisioning and SCIM, session and bearer authentication, and separation-of-duties RBAC on writes.

Tamper evidence

Every mutation lands in a SHA-256 hash-chained audit log. A changed or removed record breaks the chain.

Fail-closed defaults

The application refuses to start in a non-dev environment without auth enabled, a strong session secret and explicit CORS origins. Account lockout, password policy, login rate limiting and security response headers are on by default.

Provenance

Ingestion runs record the SHA-256 of their source with stats and timings; AI calls record model, provider, prompt version and input/output hashes with a citation row per passage.

Interfaces

481 REST endpoints with OpenAPI docs, a 63-template HTMX web UI, and a 26-command Typer CLI over the same service layer.

Deployment

Docker and Compose, Alembic-managed schema at a single head, and a reliability self-check for readiness.

Supply chain

CI runs ruff, mypy strict, bandit SAST and the full suite against a real Postgres, plus CycloneDX SBOM, pip-audit and Trivy. A non-conformant OSCAL export fails the build.

What landed this cycle

seventeen pull requests, all merged

The cycle's theme was foundations: the ontology that removes per-framework narrative duplication, and the posture spine that gives machine evidence somewhere to land. Both were sequenced deliberately ahead of the features that need them.

Shipped

Capability ontology

A capability is authored once and carries edges to the canonical control, system components, risks and indicators. One capability annotating three controls reaches CMMC, FedRAMP and ISO through the existing crosswalk — verified end to end.

Status derivation writes a sibling field and never creates a row, so derived signal can never quietly assert something about a control nobody claimed.

Shipped

SSP narrative from capability

Edit one capability, re-render every control it maps to. This is the duplication the ontology existed to remove, now visible in the product.

Shipped

Per-resource posture findings

A check now names which resources failed rather than returning a single verdict, and a deterministic check beats a model verdict where both exist. It writes through the existing control-test path — one results table, one vocabulary, one POA&M loop.

Shipped

Live provider posture

Microsoft 365 / Graph: MFA registration, legacy authentication blocked, stale accounts. PuppetDB: whether the fleet is reporting, and whether declared state is actually being enforced.

Report-only enforcement does not satisfy a check, and a missing API permission reports as unrunnable — a 403 must never read as a clean fleet.

Shipped

Desired state as data

Posture checks are declared in packs rather than coded, and pack sources can be polled from a Git repository and adopted on review — GitOps for compliance content.

Shipped

Closed-loop remediation, waivers, drift

A failing check produces a remediation plan and closes when it recovers; a finding can be waived with an approver instead of deleted; drift is retained on a schedule; and change impact answers what a configuration change would do to the authorization before it is made.

One defect fixed along the way: the failing-resources view was reporting resources that had already been fixed.

Shipped

Flaw remediation against SI-2

Remediation measured against declared timeframes and organized into waves. Formally accepted risk became its own bucket rather than an SLA breach.

Operators should know: the compliance percentage can fall on the first read after upgrade. A young accepted-risk POA&M used to count as compliant — accepted on day three and credited as remediated. The same rows are now counted honestly.

Shipped

DISA CCI as an authoritative source

5,149 CCIs and all 10,216 of their references across 800-53 v3, Rev 4, Rev 5 and 800-53A, with the reverse index the platform lacked: a scanner finding that names only a CCI now resolves to controls.

Shipped

Live catalog sources

Upstream OSCAL is polled with conditional requests and content hashing, revisions are retained, and adoption is gated on human review. Detection and loading used to be disconnected; they are now joined.

Hardened

Two critical unauthenticated RCEs

Patched in the landing site's dependency tree, along with six other advisories. Both dependency trees are now clear.

Hardened

Role names the system cannot hold

Several routes named roles outside the actual role enum, which silently collapsed to admin-only — endpoints that read as broader than they were. Corrected, and the same defect was found and fixed in the waiver approver list.

In flight

not yet in the main line
Shipped

CR26 schema spine

Merged. FedRAMP's eleven CR26 schemas are vendored and pinned by SHA-256, documents validate against them entirely offline, and the eleven are watched for upstream drift.

One measured caveat that shapes everything built on top: this environment enforces the date format but not date-time or uri, because the optional validator libraries are absent. A malformed timestamp therefore validates clean. The seeders below are written to be correct by construction rather than trusting the validator to catch it, and every date they emit is pinned by an exact-string test.

Shipped

CR26 deliverables — five of eleven

The Certification Package Overview and the Security Decision Record are generated from what the platform already holds: SSP control narrative, assigned parameter values, KSI validation results and assessor findings. Authoring is admin-only, and a re-seed refreshes every derived field while preserving the one thing the platform cannot derive — the human-written narrative.

The three Vulnerability Evaluation and Reporting documents — Vulnerability Detail Report, Accepted Vulnerability Info, and the machine-readable historical record — are generated from the POA&M table. These carry the programme's earliest deadline: mandatory 2026-12-07, ahead of CPO and SDR maintenance.

A seeded document reports what it could not say. A vulnerability with no identification date, no detection source or no description is left out and named, because the deliverable's own to-do list is worth more to an operator than a document that quietly looks complete.

Shipped

CR26 vocabulary

Already merged. CR26 replaces the provider-side POA&M with a list of Accepted Weaknesses — and the platform already stored the weakness, so nothing about what is stored changed. An existing POA&M row classifies as accepted, not accepted, or unknown, with no second table to disagree with the first.

Certification Class (A–D) and Path are stored as independent axes. FedRAMP is explicit that a Class is not a replacement for an impact level, and the published ranges overlap — so nothing derives one from the other, and a build guard fails the build if anything starts to.

What the build will not claim

read this before a customer conversation

These are current boundaries, not defects. Each is a place where the product could be oversold, so each is stated plainly.

Limit

Live machine evidence is two providers deep

Five automated posture checks across Microsoft 365 / Graph and PuppetDB. AWS GovCloud captures configuration but has no checks evaluating it; Azure and GCP have no connector at all. Everything else is human-attested or ingested evidence.

The spine that machine evidence lands on is built and tested — adding a provider is now additive work rather than architecture.

Limit

The M365 checks have not been run against a live tenant

Evaluators are pure and tested against recorded Graph responses. Confirming a check reads a given tenant requires that tenant's app registration, which the team does not hold.

Limit

AI proposes; it never decides

The model layer is optional and off by default. It drafts narrative and proposes findings, always marked as draft, always citation-bearing, and an assessor's acceptance is the only path to an authoritative record. There is deliberately no open-ended assistant over project data.

Limit

There is no official FedRAMP 20x OSCAL package

FedRAMP publishes requirements; NIST publishes OSCAL; Concord generates its own. The community-maintained KSI catalog is not the system of record here, and should not be described as one.

Limit

The README's status section is stale

It still reports 54 migrations and 720-plus tests against an actual 79 and 2,745. Nothing in the product is wrong — the summary prose simply has not kept up with two cycles of work. Worth correcting before it is quoted somewhere that matters.

Limit

An acceptance rationale lives inside the document it appears in

CR26 requires a written rationale for every accepted vulnerability, and no column in the platform holds one — so an administrator authors it into the deliverable, and each re-seed preserves it. That works until a reporting window moves backwards past an accepted vulnerability: the row falls outside the new period, the stored document is replaced, and the rationale is gone with nothing reported at the moment it happens.

It is named here rather than smoothed over because it is the one place in this family where work disappears silently, and that is precisely what the rest of the design exists to prevent. The fix is to give the rationale a durable home of its own rather than a home inside a generated document. Until then: do not move a reporting window backwards past an accepted vulnerability without re-authoring afterwards.

What comes next

sequenced, not a wish list

The foundations were built first precisely so this list is additive. In rough dependency order:

  • Provider breadth — Azure Government and GCP connectors, and posture checks over the AWS GovCloud capture that already exists. This is the single change that most moves the continuous-verification story.
  • Gap assessment and Trust Center depth — now possible, because the ontology finally gives them something to compare and something to publish.
  • Assessment depth — objective-level SAR findings, a generated OSCAL assessment plan, and a FedRAMP Rev 5 baseline overlay with assigned parameter values.
  • Identity and crypto hardening — MFA and PIV-CAC, SSO hardening, KMS-backed key rotation and FIPS-validated cryptography.
  • CR26 completeness — the Security Decision Record's fedRampRequirements is the last unfilled field on a shipped deliverable. It is not blocked on sourcing FedRAMP's rule identifiers, as first thought: the schema leaves that id an unconstrained string and asks, per requirement, for a written description of how the provider meets it. That is authored work, not generated — the same shape as the narrative and rationale fields already handled — so it needs an authoring surface, not a lookup table.
  • Integrations — eMASS, Jira, and wiring the typed AI action path to the organization's own gateway.

The one thing to take from this report: the product is broad and the foundations are now right, but breadth of live machine evidence is the gap between "a compliance program that runs in Concord" and "an authorization Concord continuously verifies." Everything needed to close it is built. What remains is providers.
